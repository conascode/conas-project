요약

v1은 기능 요구사항을 모두 충족하지만 메모 창을 Chromium 기반 WebView2로 그린다. 실사용 중인 v1.1 설치본(메모 2개, 접힘)은 프로세스 7개, 개인 메모리 121.9 MB(3회 중앙값) 측정를 쓰고, 그중 앱 자신의 Rust 프로세스는 5.8 MB 측정로 비용의 95 % 이상이 WebView2 런타임에서 나온다. 통제 조건 측정(Rev 1.0, v1.0 코드)에서는 메모 1개 99.1 MB, 포커스된 메모의 유휴 CPU 1코어 1.55 %, 타이핑 CPU 28 % 측정였다. 또 v1은 메모리를 줄이려고 WebView2의 GPU 사용을 강제로 끄며(실행 인자로 확인 측정), 이는 v2 지침이 금지하는 방식이다.

Rev 2.0은 하룻밤 사이 추가된 v1.1 기능(서식, 사진, 붙여넣기 정리, 잠금, 전체화면, 메모별 작업표시줄, 자동 실행 복구, 진단 로그)을 반영해 전면 개정한 것이다. v1의 구조·기능·데이터를 전부 목록화하고(기능 36개, IPC 명령 19개 + URI 스킴 1개, 이벤트 4개, 저장 필드 20개 + 좌표 4개 + 사진 파일), WebView2를 제거한 단일 프로세스 Win32 아키텍처를 설계한다. v1.1의 서식·사진 기능 때문에 본문 컨트롤은 평문 EDIT가 아니라 OS 내장 RichEdit(MSFTEDIT)로 바뀌었다 — 여전히 Native Edit Control이며 IME·실행 취소를 OS가 제공한다. 목표는 트레이 대기 개인 메모리 3 MB 이하, 메모 10개(사진 제외) 14 MB 이하, 유휴 CPU 사실상 0 % 목표이다. GDI 대 Direct2D, 사진 객체 구현 방식은 결론을 미리 정하지 않고 6.7절 프로토타입으로 실측해 결정한다. 저장소는 SQLite로 옮기되 v1 데이터는 원본을 보존한 채 한 번의 트랜잭션으로 가져오고, 사진 폴더는 그대로 공유한다.

1.Executive Summary

1.1 결론

  • 재개발은 타당하다. v1.1 실사용 인스턴스 메모리의 95 % 이상(121.9 MB 중 116.1 MB)과 유휴 CPU의 전부가 WebView2 프로세스에서 발생한다 측정. 앱 코드 최적화로는 줄일 수 없는 비용이다(3.7절).
  • 기능은 그대로 재현된다 — 1건은 사용자 결정으로 단순화. 36개 기능 중 31개는 Win32·RichEdit 표준 기능으로 직접 재현된다. P0 프로토타입에서 사진 이름 보존·폭 맞춤을 실측으로 해결했고(PT-D′), 움직이는 GIF는 첫 프레임 정지 표시로 사용자가 결정했다(2026-11-14, 파일은 그대로 보존). P1에서 메모·목록·메뉴·확인 카드를 다시 만들어 v1.1과 픽셀 단위로 비교했고(13.6절), 남은 차이는 글자 래스터화 수준이다. 선택 영역 색·캐럿 색은 시스템 기본을 쓰기로 사용자가 승인했다(허용 차이 A7·A8, 2026-11-14).
  • 본문은 RichEdit, 저장 형식은 v1.1 서식 HTML 그대로. 굵게·기울임·밑줄·취소선·글머리·사진은 평문 EDIT로 재현할 수 없다. RichEdit은 OS 내장 컨트롤이라 런타임 추가가 없고 다단계 실행 취소와 TSF IME를 제공해 Rev 1.0의 위험 R1 일부가 해소된다(6.4절).
  • v1 Rust 코드의 약 3분의 1을 재사용한다. 데이터 모델·가져오기·자동 실행·사진 저장소·로그·앵커·모니터 보정·입력 규칙(약 900행)은 WebView와 무관하다. JS 허용 목록 정리기(rich.js)는 Rust로 이식한다(4.4절).
  • 저장소는 SQLite로 옮긴다. 메모 단위 갱신으로 파일 전체 재작성을 없애고 무결성 검사·백업 복원 경로를 갖춘다. v1 notes.json은 지우지 않고, images\ 폴더는 v1·v2가 같이 쓴다(10·12·16장).
  • 렌더링은 GDI로 확정했다(P0). 크롬+RichEdit 프로토타입이 메모 1/10/50개에서 2.22/2.30/2.98 MB, 유휴 CPU 0 % 측정. Direct2D는 1회 비용만 +27 MB 이상이라 탈락(13.5절).

2.Project Overview

2.1 배경

GaeunMemo는 Windows 바탕화면 스티커 메모 앱이다. 메모 하나가 프레임 없는 독립 창 하나이며, 트레이에 상주하고 컴퓨터를 켤 때 자동 실행된다. 즉 하루 종일, 수 주 동안 켜져 있는 상주형 프로그램이므로 유휴 상태의 메모리·CPU 비용이 사용자 체감 비용의 대부분을 차지한다.

v1.0은 2026-11-13 하루 동안 Rust + Tauri 2로 개발되었고, 같은 날 밤부터 11-14 오전 사이 v1.1(서식·사진·잠금·전체화면·메모별 작업표시줄)이 추가되었다. 개발 과정에서 메모리를 줄이기 위해 (1) 모든 창이 렌더러 하나를 공유하도록 하고 (2) GPU를 꺼서 메모 10개 기준 개인 메모리를 468 MB → 140 MB 측정로 줄였으나, 남은 비용은 WebView2 구조에서 나오며 (2)는 v2 지침이 금지한다.

v1.1에서 기능 범위가 "평문 스티커"에서 "서식·사진이 있는 메모"로 넓어졌다. v2 설계에 미치는 영향은 본문 컨트롤(RichEdit), 서식 변환기·붙여넣기 정리기 이식, 사진 디코딩·메모리 관리, 작업표시줄 구조 네 가지다.

2.2 범위 (Phase 1)

  • 포함: v1.1 구조·의존성·UI·기능·데이터 분석, 성능 기준선 측정, v2 아키텍처, 마이그레이션 계획, GDI/Direct2D·RichEdit·사진 객체 프로토타입 설계, 구현 계획.
  • 제외: v2 코드 작성(Phase 2 이후), 설치 관리자 제작, 코드 서명.

5.2 프로세스·스레드 모델과 근거

결정 A-1. 단일 프로세스, 단일 UI 스레드. 모든 메모 창·목록 창·팝업·세션 창·트레이는 하나의 UI 스레드가 소유한다. Win32에서 창은 생성한 스레드의 메시지 큐에 묶이므로, 한 스레드로 두면 창 간 상태 공유에 잠금이 필요 없다. 대안: 창마다 스레드 — 창 간 Z순서·포커스 동기화가 복잡해지고 스레드당 스택 1 MB 예약(커밋은 작음)이 생겨 이득이 없다.
결정 A-2. 저장은 전용 스레드. SQLite 커밋은 synchronous=FULL에서 fsync를 동반하므로 수 ms 이상 걸릴 수 있다 예상. UI 스레드는 변경 내용을 값(소유 데이터)으로 복사해 채널로 보내고 즉시 복귀한다. 사진 파일 쓰기도 같은 FIFO 채널로 보내 "사진 파일이 그것을 참조하는 메모 행보다 먼저 디스크에 있다"는 순서를 구조로 보장한다. 대안: UI 스레드 동기 쓰기 — 지침 9 위반, 디스크 지연이 입력 지연으로 전파.
결정 A-3. 사진 디코딩은 별도 스레드, 지연 생성. 25 MB JPG 디코딩은 수십~수백 ms가 걸릴 수 있다 예상. 디코딩 스레드는 첫 사진 표시 요청 때 만들고 큐가 60 s 비면 종료한다. 결과는 표시 크기 DIB로 UI에 넘기며, 그동안 객체는 크기만 잡힌 빈 사각형으로 그린다(크기는 DB note_image.w/h 캐시, 11.1절). 대안: 저장 스레드에서 디코딩 — 쓰기 지연이 커짐. 스레드 풀 — 의존성 증가, 이득 없음.

6.6 그리기 구조

본문 영역은 RichEdit이 스스로 그리고, 부모는 띠·제목 줄·서식 줄·테두리만 그린다. 창마다 클라이언트 크기의 메모리 DC 비트맵을 상시 보관하지 않는다. WM_PAINT 동안만 무효 영역 크기의 호환 비트맵을 만들고 해제하거나, UI 스레드 공용 백버퍼(최대 창 크기) 1개를 재사용한다(13.4절 실측 비교 항목). 글꼴·브러시·펜은 (테마, DPI) 조합별로 1벌만 만들어 모든 창이 공유하며, 창 수에 비례하는 GDI 개체는 창 DC와 RichEdit 자체뿐이 되도록 한다. 아이콘(핀 2상태, +, ⋯, ×, 체크)은 DPI별 32bpp 프리멀티플라이드 비트맵을 실행 시 1회 래스터화해 AlphaBlend로 그린다.

측정 도구와 판정

  • 메모리: GetProcessMemoryInfo(PrivateUsage, WorkingSet), 1 s 간격 샘플.
  • CPU: 프로세스 CPU 시간 증가량, 깨어남은 WPR/WPA(CPU Usage Precise).
  • 그리기: QueryPerformanceCounter로 WM_PAINT 구간 계측(빌드 기능 플래그).
  • 자원: GetGuiResources(GR_GDIOBJECTS/GR_USEROBJECTS), 핸들 수.

  • 판정 규칙 (사진): PT-D가 ① 이름을 손실 없이 읽고 ② 표시 크기 기준 메모리(8.2절)를 지키며 ③ 실행 취소·복사·끌기에서 이름이 유지되면 PT-D(코드가 적음). 하나라도 실패하면 PT-E. GIF 애니메이션은 PT-E에서만 가능할 것으로 예상되며, PT-D 채택 시 GIF 처리 방식은 사용자 결정 항목(7.4절). 결과: 원본 스트림 PT-D는 ②에서 탈락(파일 크기 비례 메모리), 표시 크기 재인코딩 PT-D′는 ①–④ 통과 측정 → PT-D′ 채택. RichEdit은 GIF를 재생하지 않음 측정 → 사용자 결정: 정지 표시.
  • GPU 정책: PT-B는 하드웨어 렌더 타깃 기본, 실패·장치 손실 시 WARP 대체. 메모리를 이유로 GPU를 강제로 끄지 않는다(지침).
  • P0 결과(13.5절): PT-A 채택 — PT-B·PT-B′는 1회 비용만 +27 MB 이상으로 규칙의 10배 측정. 사진은 PT-D′ 채택, PT-E 불필요. GDI를 고른 것은 측정된 메모리 때문이며 GPU를 끄는 설정이 아니다(GDI 경로는 GPU 장치를 만들지 않을 뿐).

RichEdit 지연 로드msftedit.dll은 첫 메모 창 생성 때 로드. 모든 메모를 닫아도 해제하지 않음(재로드 비용·불안정 회피).시작 시 로드: 트레이만 상태 비용 증가. 매번 해제: FreeLibrary 후 재로드 지연.
사진 (PT-D′)디코딩 스레드가 WIC 스케일러로 표시 픽셀 크기에 맞춘 JPEG/PNG를 만들어 RichEdit에 넣는다. RichEdit은 이 작은 압축본(4000×3000 사진 → 34.6 KB)과 화면에 그린 표시 크기 비트맵만 보유한다 측정. 전체화면 등 표시 폭이 바뀌면 원본 파일에서 다시 만들어 재삽입(1.1 ms, 실행 취소 기록 중지). 원본 바이트는 저장 스레드로 넘긴 뒤 UI가 들고 있지 않음. GIF는 첫 프레임만.원본 해상도 디코딩: 4000×3000 = 48 MB/장 예상. 축소판 파일 캐시: 디스크·정리 대상 증가.
GDI 자원 공유글꼴(제목 700/13.5, 본문 400/size, 메뉴 13, 목록 3종)과 브러시를 (테마, DPI, 크기) 키로 캐시. 참조 수 0이 되면 해제(글자 크기 변경 시 사용하지 않는 크기 정리).창마다 생성: 메모 50개면 GDI 개체 수백 개.
백버퍼 정책상시 창별 비트맵 금지. WM_PAINT 중 무효 영역만 임시 비트맵 또는 공용 1개(13.4 실측 후 결정).창별 상시 백버퍼: 260×260×4 B×(1.5²) ≈ 0.6 MB/창 예상.
닫힌 메모닫힌 메모는 HWND·RichEdit를 만들지 않는다. 목록용 요약(제목, 첫 줄 100자, 색, 시각)만 메모리에 두고 본문은 열 때 DB에서 읽는다.전 메모 본문 상주: 메모 수 × 평균 크기.
할당자Rust 기본 시스템 할당자(HeapAlloc). 할당 빈도가 낮아 별도 할당자 불필요.mimalloc 등: 크기 증가, 이득 없음 예상.
작업 집합 트림사용하지 않음. 트레이 숨김 시 SetProcessWorkingSetSize(-1,-1)는 지표만 낮추고 재접근 시 페이지 폴트 → 측정 왜곡.—

8.3 누수 방지와 검증

  • 모든 Win32 핸들(HFONT, HBRUSH, HBITMAP, HDC, HICON, HMENU)은 RAII 래퍼(Drop에서 DeleteObject/DestroyIcon 등)로 감싼다. 원시 핸들 노출은 render 모듈 내부로 한정. COM 포인터(TOM, WIC, OLE 객체)는 windows 크레이트의 참조 계수 타입으로만 보유하고, 창 파괴 시 EM_SETOLECALLBACK(NULL) → TOM 해제 순서를 지킨다(순환 참조 방지).
  • 창 상태는 Box::into_raw로 GWLP_USERDATA에 저장하고 WM_NCDESTROY에서 Box::from_raw로 회수(이중 해제 방지 위해 포인터 0으로 재설정).
  • 합격 기준: 50개 생성·삭제 1,000회 후 GDI 개체 수·USER 개체 수·핸들 수가 시작값 ±2 이내, 사진 10장 메모 열기·닫기 200회 후 개인 메모리 시작값 +1 MB 이내, 72시간 상주 시 개인 메모리 증가 ≤ 1 MB 목표(14·18장).

9.CPU and Rendering Optimization

9.1 유휴 0 원칙

  • 타이머 없음: 상주 중 주기 타이머를 두지 않는다. 예외는 목록 창이 보일 때의 60 s "n분 전" 갱신 하나뿐(v1.1은 목록이 열려 있는 동안 setInterval). 움직이는 GIF는 정지 표시로 결정되어 프레임 타이머가 없다. 직렬화·"✓ 복사됨"은 1회성 타이머.
  • 폴링 없음: 저장 스레드는 채널 recv/recv_timeout에서 커널 대기. 대기할 deadline이 없으면 무기한 대기.
  • 캐럿: 포커스된 RichEdit의 캐럿 깜빡임(기본 530 ms)은 OS 동작으로 남는다. v1 유휴 CPU는 포커스된 메모(v1.0) 1.55 %, 포커스 없는 접힌 메모(v1.1) 0.05 % 측정로 30배 차이가 났다 — 깜빡임에 따른 Chromium 합성이 유력한 원인이나 조건이 달라 단정하지 않는다 미확인. v2에서는 캐럿 영역만 다시 그려지므로 비용이 작다 예상. P2에서 실측.
  • 애니메이션 없음: 도구 표시 전환, 메뉴 열림에 애니메이션을 쓰지 않는다.

9.2 그리기 비용 통제

  • 무효화 단위 최소화: hover 변경 → 해당 도구 버튼 24×24만, 제목 변경 → 제목 줄만, 테마 전환 → 전 창 1회.
  • 이동 중 재그리기 없음: HTCAPTION 이동은 DWM이 창 비트맵을 옮김(클라이언트 재그리기 불필요).
  • 크기 조절: WM_SIZE에서 레이아웃 재계산 후 RichEdit MoveWindow(..., FALSE) + 한 번의 InvalidateRect. WM_EXITSIZEMOVE에서만 저장.
  • 목록: 보이는 행만 그림, 필터는 입력 후 즉시(메모 1,000개 기준 1 ms 이하 목표).

11.Threading and Event Processing

11.1 규칙

  • UI 스레드만 HWND·GDI·RichEdit·TOM·OLE 객체·앱 상태를 만진다(OleInitialize, STA). 다른 스레드는 PostMessageW로만 UI에 알린다.
  • UI → 저장: std::sync::mpsc::Sender<StoreCmd>. 값은 소유 데이터로 복사되어 공유 상태·잠금이 없다(v1은 Mutex<Data>를 양쪽이 잠금).
  • UI → 디코딩: DecodeReq { note, image, name, target_px }. 디코딩 스레드는 CoInitializeEx(MTA)로 WIC만 사용, 결과 DIB(HBITMAP이 아닌 메모리 버퍼)를 WM_APP_DECODED로 넘기고 UI가 CreateDIBSection. 늦게 도착한 결과(창 닫힘·크기 바뀜)는 세대 번호로 버림.
  • UI 스레드에서 금지: 파일 I/O, SQLite 호출, 사진 디코딩·인코딩, 네트워크, Sleep, 1 ms 이상 걸리는 계산. 예외: 시작 시 DB 열기·로드(첫 창 표시 전 1회, 10 ms 이하 목표), 직렬화(5.4절 목표 이내), 클립보드·끌어놓기 데이터 읽기(OLE가 UI 스레드 요구, 바이트는 즉시 저장 스레드로 넘김). 사진 자리 크기는 DB의 note_image.w/h 캐시로 알므로 UI가 파일을 열지 않는다(캐시 없는 v1.1 사진은 디코딩 스레드가 첫 결과와 함께 크기를 알려 채움).
  • 모달 루프(TrackPopupMenu, 이동·크기 조절, 확인 카드) 중에도 저장 스레드는 독립적으로 진행.
  • panic 정책: 릴리스는 panic="abort"(v1 동일). 모든 WndProc 진입부는 Result를 반환하는 내부 함수로 위임하고 오류는 기록 후 기본 처리로 진행 — FFI 경계에서 unwinding이 발생하지 않도록 한다.
