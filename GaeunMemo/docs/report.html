요약

v1은 기능 요구사항을 모두 충족하지만, 메모 창을 그리는 데 Chromium 기반 WebView2를 사용하기 때문에 메모 1개만 열어도 프로세스 7개, 개인 메모리 약 99 MB 측정를 사용하고, 아무 입력이 없을 때도 CPU 한 코어의 약 1.5 % 측정를 계속 소모한다. 이 중 앱 자신의 Rust 코드가 쓰는 개인 메모리는 4.9 MB 측정로, 비용의 95 % 이상이 WebView2 런타임에서 발생한다. 또 v1은 메모리를 줄이려고 WebView2의 GPU 사용을 강제로 끄고 있으며, 이는 v2 지침이 금지하는 방식이다.

본 보고서는 v1의 구조·기능·데이터를 전부 목록화하고(기능 28개, IPC 명령 16개, 이벤트 4개, 저장 필드 16개 + 좌표 4개), WebView2를 완전히 제거한 단일 프로세스 Win32 아키텍처를 설계한다. 설계 목표는 트레이 대기 시 개인 메모리 3 MB 이하, 메모 10개 12 MB 이하, 유휴 CPU 사실상 0 % 목표이다. 렌더링 방식(GDI 대 Direct2D)과 본문 컨트롤(EDIT 대 RichEdit)은 결론을 미리 정하지 않고, 6장·13장에 정의한 프로토타입으로 실측해 결정한다. 저장소는 SQLite로 옮기되 v1 데이터는 원본을 보존한 채 한 번의 트랜잭션으로 가져온다.

1.Executive Summary

1.1 결론

  • 재개발은 타당하다. v1 메모리의 95 % 이상, 유휴 CPU의 사실상 전부가 WebView2 런타임에서 발생한다 측정. 앱 코드 최적화로는 줄일 수 없는 비용이다(3.7절).
  • 기능 손실 없이 재현 가능하다. 28개 기능 중 25개는 Win32 표준 기능으로 직접 재현되고, 3개(선택 영역 색, 커서 색, 다단계 실행 취소)는 컨트롤 선택에 따라 추가 구현이 필요하다(7.4절).
  • v1 Rust 코드의 약 40 %는 재사용한다. 데이터 모델·가져오기·자동 실행·앵커 창·모니터 보정 로직(약 700행)은 WebView와 무관하다(4.4절).
  • 저장소는 SQLite로 옮긴다. 메모 단위 갱신으로 파일 전체 재작성을 없애고, 무결성 검사와 백업 복원 경로를 갖춘다. v1 notes.json은 지우지 않는다(10·12·16장).
  • 렌더링은 실측 후 결정한다. 기본은 GDI + Native EDIT. Direct2D는 프로토타입에서 이득이 측정될 때만 채택한다(6.7절, 13장).

2.Project Overview

2.1 배경

GaeunMemo는 Windows 바탕화면 스티커 메모 앱이다. 메모 하나가 프레임 없는 독립 창 하나이며, 트레이에 상주하고 컴퓨터를 켤 때 자동 실행된다. 즉 하루 종일, 수 주 동안 켜져 있는 상주형 프로그램이므로 유휴 상태의 메모리·CPU 비용이 사용자 체감 비용의 대부분을 차지한다.

v1은 2026-11-13 하루 동안 Rust + Tauri 2로 개발되었고 요구 기능을 모두 갖췄다. 개발 과정에서 메모리를 줄이기 위해 (1) 모든 창이 렌더러 하나를 공유하도록 하고 (2) GPU를 꺼서 메모 10개 기준 개인 메모리를 468 MB → 140 MB 측정로 줄였으나, 남은 비용은 WebView2 구조에서 나오며 (2)는 v2 지침이 금지한다.

2.2 범위 (Phase 1)

  • 제외: v2 코드 작성(Phase 2 이후), 설치 관리자 제작, 코드 서명.

5.2 프로세스·스레드 모델과 근거

결정 A-1. 단일 프로세스, 단일 UI 스레드. 모든 메모 창·목록 창·팝업·앵커·트레이는 하나의 UI 스레드가 소유한다. Win32에서 창은 생성한 스레드의 메시지 큐에 묶이므로, 한 스레드로 두면 창 간 상태 공유에 잠금이 필요 없다. 대안: 창마다 스레드 — 창 간 Z순서·포커스 동기화가 복잡해지고 스레드당 스택 1 MB 예약(커밋은 작음)이 생겨 이득이 없다.
결정 A-2. 저장은 전용 스레드. SQLite 커밋은 synchronous=FULL에서 fsync를 동반하므로 수 ms 이상 걸릴 수 있다 예상. UI 스레드는 변경 내용을 값(소유 데이터)으로 복사해 채널로 보내고 즉시 복귀한다. 대안: UI 스레드 동기 쓰기 — 지침 9 위반, 디스크 지연이 입력 지연으로 전파.

9.CPU and Rendering Optimization

9.1 유휴 0 원칙

  • 타이머 없음: 상주 중 주기 타이머를 두지 않는다. 유일한 예외는 목록 창이 보일 때의 60 s "n분 전" 갱신(숨기면 해제).
  • 폴링 없음: 저장 스레드는 채널 recv/recv_timeout에서 커널 대기. 대기할 deadline이 없으면 무기한 대기.
  • 캐럿: 포커스된 EDIT의 캐럿 깜빡임(기본 530 ms)은 OS 동작으로 남는다. v1 유휴 1.5 %의 유력 원인이 이 깜빡임에 따른 Chromium 합성이라면 미확인, v2에서는 EDIT가 캐럿 영역만 XOR로 그리므로 비용이 작다 예상. P2에서 실측.
  • 애니메이션 없음: 도구 표시 전환, 메뉴 열림에 애니메이션을 쓰지 않는다.

9.2 그리기 비용 통제

  • 무효화 단위 최소화: hover 변경 → 해당 도구 버튼 24×24만, 제목 변경 → 제목 줄만, 테마 전환 → 전 창 1회.

  • 크기 조절: WM_SIZE에서 레이아웃 재계산 후 EDIT MoveWindow(..., FALSE) + 한 번의 InvalidateRect. WM_EXITSIZEMOVE에서만 저장.

11.Threading and Event Processing

11.1 규칙

  • UI 스레드만 HWND·GDI·앱 상태를 만진다. 다른 스레드는 PostMessageW로만 UI에 알린다.
  • UI → 저장: std::sync::mpsc::Sender<StoreCmd>. 값은 소유 데이터로 복사되어 공유 상태·잠금이 없다(v1은 Mutex<Data>를 양쪽이 잠금).
  • UI 스레드에서 금지: 파일 I/O, SQLite 호출, 네트워크, Sleep, 1 ms 이상 걸리는 계산. 예외는 시작 시 DB 열기·로드(첫 창 표시 전 1회, 10 ms 이하 목표).
  • 모달 루프(TrackPopupMenu, 이동·크기 조절, 확인 카드) 중에도 저장 스레드는 독립적으로 진행.
  • panic 정책: 릴리스는 panic="abort"(v1 동일). 모든 WndProc 진입부는 Result를 반환하는 내부 함수로 위임하고 오류는 기록 후 기본 처리로 진행 — FFI 경계에서 unwinding이 발생하지 않도록 한다.
